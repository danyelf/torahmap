# Handoff — 14 September 2026

Where the project stands, what was decided and why, and the traps that cost real
time to find. Written so this work survives losing the session it came from.

A formatted version of this document is published as an artifact; this file is
the copy that lives with the code.

## The situation in one paragraph

On 4 September two things blocked shipping: search was annoying, and there was
no way in. The way in shipped — scrollytelling is on main. The search fix is
designed, its data layer has been replaced underneath it, and **none of it is
built**. Everything landed since has been foundation, none of which a reader
sees.

## What is not built

Click-to-search does not exist. There are no word spans in the verse display, no
click handling, no menu, and results still render in a floating box capped at
60% of viewport height. This was checked across main, the scrollytelling branch
and the higher-contrast branch — `src/sidebar.ts` has no word-level handling
anywhere, and neither does the Talmud view.

Two things are clickable today and are easy to mistake for it: a search result
row, which pins that verse, and a related-word chip, which runs that word as a
search.

The remaining build is one span per word in the verse popup, a menu on click,
and results moved into the full-height right panel grouped by book.
`getWordBoundaries()` in `src/search.ts` already splits Hebrew correctly,
including maqaf (U+05BE), which is the fiddly part.

## Decisions, and the evidence behind them

The full design is in `2026-09-04-search-redesign-design.md`. The reasoning
matters more than the conclusions, because twice in one session a rejected idea
was nearly rebuilt after the reasoning was forgotten.

**Hebrew is reached by typing Hebrew, or by clicking a word. Nothing else.** The
virtual keyboard and the transliteration layer are deleted rather than improved
— about a thousand lines and the `simple-keyboard` dependency. Done in PR #97,
which also removed the א button and the hidden script mode that had been
silently deleting wrong-script characters as you typed; the project now has no
runtime dependencies at all. Issues #46 and #48 were closed with it.

The evidence is the part to keep. Resolving loose input into a short candidate
list was measured against the real corpus of 44,740 written forms. Over the
2,000 most frequent — the words people would actually search — the median query
matches 45 different words and only 3.5% resolve to a single answer. Hebrew does
not write most vowels, so every word built on the letter resh collapses into a
pile of 218. This is a property of the language, not of the matching rules, and
no tuning changes it.

An earlier probe appeared to show the opposite, reporting the right answer
inside the top five for all fifteen test words. That result was worthless: the
same fifteen words were used to tune the rules and to evaluate them, and they
were all long, consonant-rich proper nouns whose skeletons are unusually rare.

**Clicking a word opens a menu. It never leaps.** Nothing happens until the
reader picks an item. Overlays are mutually exclusive and `setOverlay()` calls
`destroy()` on the outgoing one, so a bare click while reading Haftarah would
silently discard that view and its settings. The menu makes the loss
deliberate. An undo button would not have worked, because by then the state is
gone.

**Colour belongs to the word; meaning is an optional filter inside it.** Senses
never get colours. A word with only one sense shows no control at all. Ten
senses of a word still paint one colour, so the five-colour palette limits how
many *words* can be compared, which is what it should limit.

**Results are ordered by book, never by relevance.** Applying a relevance score
to scripture is a judgement the app declines to make. This settles the
multi-term case too, which interleaves in book order.

**The 1894 concordance index is gone from the project entirely** — data, code,
tests, documentation. Words are identified by ETCBC/BHSA lexemes. The written
form עלה had been offered five entries, one of which was the Aramaic preposition
"upon", a different word sharing a spelling. Homograph separation removes the
need for the root-comparison heuristic rather than improving it.

## Traps

Each of these cost real time and none is discoverable by reading the code.

**Fresh worktrees have no `node_modules`.** Typecheck then fails with
`Cannot find type definition file for 'vite/client'`, which looks like a code
error and is not. `work-on-issue.sh` now installs dependencies and the hooks.

**`~/.npmrc` sets `ignore-scripts=true`** on this machine, so npm's `prepare`
silently does nothing. Hook setup is the explicit `./scripts/install-hooks.sh`.
This was caught only by testing a genuinely fresh clone.

**`core.hooksPath` must stay relative.** It is one repository-wide setting
shared by every worktree, and git resolves a relative value against whichever
tree is committing. The old tracker pinned it to an absolute path, which is
exactly why every worktree ran the same dead hook.

**happy-dom's `NodeList.forEach` could silently visit nothing.** Resolved, and
recorded because the shape recurs. `simple-keyboard` pulled in core-js, whose
polyfill replaced the method; happy-dom keeps its nodes behind a Proxy, so
`length` reported 8 and `forEach` visited 0. Tests passed or failed depending on
what else had been imported. It was pinned in the test setup file, and deleting
the keyboard took core-js out of the tree, so the pin went with it. Any future
dependency that ships core-js brings this back.

**Changing the hash in a loaded tab does not re-run `main()`.** An overlay then
carries state from the previous step, so a restore looks like it worked when it
did not. Verify restores in a fresh tab. This produced a false "verified" claim
that survived two rounds of review.

**Agent-started dev servers get reaped**, three times in one session, reporting
low memory while the machine had 54% free. Start one by hand when you want to
look at something.

## Open questions

- **#72** — is search a core feature or an overlay? The click-to-search menu
  exists only because it is an overlay; if it were not, the view might not be
  lost at all.
- **#77** — overlays should be discovered rather than listed in a hand-written
  array.
- **#73, #74, #75** — contract gaps found reviewing #69: parameters validated
  inbound but not outbound, an absent parameter not resetting to its default,
  and `typecheck` being unable to see test files.
- **#65** — no LICENSE file exists.
- Filtering by meaning needs real word senses. ETCBC has none; MACULA Hebrew
  carries them on roughly 38% of tokens.

(Hebrew keyboard, transliteration, search)". Two thirds of that disappears with
the keyboard. The harness should survive — it is the only way to exercise search
